# Body OS｜信息架构与主流程

> 这份文档回答一个问题:**这个 App 是怎么组织的,人要走的每一步在哪。**
> docs/01 是逐页的视觉/交互规格,这份是它上面那层 —— 页面属于谁、从哪进、走完回哪。
> 页面改完之后如果和这里对不上,先改这份,再改代码(不然下一个人还是会按旧结构加东西)。

## 一、这个 App 在做什么

一句话:**记下来 → 看见变化。**
记录的是今天发生的三件事(吃 / 练 / 身体与活动),看见的是这几件事攒出来的变化。

于是五个 tab 是五个动词,不是一个功能一个坑:

| tab | 它答的问题 | 里面装什么 |
|---|---|---|
| 首页 | 今天怎么样、今天该做什么 | 今天该练什么 + 上次那场没练完 + 身体状态分 + 能量/水分 + 活动 + 目标进度 |
| 记录 | 今天这件事记在哪 | 八类记录的入口(饮食/运动/力量训练/体重/围度/照片/喝水/食谱)+ 今天已记的 + 自动采集的数据源 |
| 速记 | 一下就能记完的那两件 | 喝水、体重 —— **不翻页**:记一笔的心理成本就是页数 |
| 趋势 | 我有没有变 | 身体(体重)· 训练(练了多少、纪录)· 饮食(热量)· 活动(步数) |
| 我的 | 我是谁、我用什么工具 | 资料与目标 + 数据源 + 健康工具箱(小工具目录) |

**「记录」和「速记」的分工是一条硬规矩**:要翻页、要选的归记录,一下记完的归速记。
同一样东西在两边都能记(比如体重),那它们必须走**同一份实现** —— 不然迟早两处记的数不一样。

## 二、三条主流程

### 1. 记一笔(饮食 / 运动 / 围度 / 照片)
```
记录 tab → 选类别 → 该类别的页面/弹层 → 保存 → 回记录(列表里能看到刚记的)
```
一眼记完的(喝水、体重)从**速记 tab** 走同一条路的短版:不翻页,记完还在这一页。
「记」和「看」分得开:围度、照片在记录页(记),在趋势页也能进(看变化)—— 两个门两种意图,
和「同一页换个筛选参数摆两格」是两回事。

### 2. 练一场
```
首页「今天练什么」卡 ─┐
                      ├→ 计划页 → 开始训练 → 逐组勾 → 结束 → 汇总 → 回首页
记录 tab「力量训练」──┘
```
- **训练的家是计划页**。记录页那格直接进它;首页那张卡由当天状态决定去哪 ——
  「今天该练」就直接开练(少点一次才是那张卡的意义),其余状态去计划页或训练记录。
  两处措辞出自同一份 `digestView`,不许各写一套。
- **今天练不了也得说得出口**。首页那张卡在小字行下面多一条「今天不练」
  (只在**今天真的该练**时出现,卡上说「练完了」「请假」时摆它等于自相矛盾):
  点它带着 `?off=1` 进计划页,由计划页把那条请假条走一遍 ——
  **记假条那套逻辑住在分包**(`engine/daynote-sheet.ts`),主包引不到,所以主包只负责送人过去,
  不自己写第二个确认框(同一个动作两套写法,两边的假条迟早不一样)。
  参数只认一次(`offAsked`),回首页看到的就是「今天请假」那张卡。
  **「今天改练」也走同一条路**(`?switch=1`):卡片说得不对时有两条出路,并排摆在一起。
  改练**不**在首页弹一层自己写的选择器,两条硬理由:①计划数据在分包,主包引不到 `engine`;
  ②计划有几天就列几项,而微信的 `showActionSheet` 只给 6 项(六天计划就爆了)。
  所以首页只送人过去,计划页那一摞训练日卡才是改练的**家**(那天的按钮顺手就把它记下了)——
  进去先在那一摞上面挂一句「挑今天要练的那套,点它底下的按钮开始」(`switchTip`,挑完自动撤),
  不然用户白跑一趟不知道要干什么。参数同样只认一次(`switchAsked`)。
- 训练中的那一场**每次都落盘**(`utils/workout-draft.ts`):被系统回收 / 被划掉也能从首页那张「继续」卡接着练。这是全站唯一一处会真丢数据的缺口,已经补上。
- 练完 → 写当天小抄(`training-digest`)+ 长程快照(`training-progress`)→ 首页与趋势页跟着更新。
- 训练的**子页**(统计/记录/肌群/器材/动作库/提醒/同步/备份/分享卡)全在计划页页脚。
  它们不属于任何一条主流程,但都属于训练;摆在计划页,进训练区一步、到子页两步。
- 「这个动作怎么做」只有一份实现(`pkg-exercise/howto/`),动作库详情和训练页速查栏共用。
  **演示图也在这半份里** —— 一张会自己循环的 GIF(库里 1324 条**每条都有**,
  所以不再有「这条有没有图」这个问题,列表上的 `演示` 蓝标也一并删了)。
  两个入口一处有一处没有,是最容易出的那种不一致。
- **动作库与计划是通的**(动作库详情 →「＋ 加入我的训练计划」→ 选一天 → 加进去),
  这是动作库存在的理由:翻到一个动作的下一步就是「我想练它」,而不是只能记住名字回计划页再搜一遍。
  两个口径写死在 `engine/editor.ts` 的 `addExerciseToDay`:**模式槽位由动作自己算**
  (在动作库里挑动作的人不知道「水平推」是什么,和编辑器里「先选模式」不同路、同一个 `addItem`),
  **认训练日的 key 不认下标**(从打开选日到点下去中间隔着用户的时间,云同步可能已经换了一份计划;
  按位置加会加到换过来的那一天上还不报错)。选日那一屏里已经有的那一天显示「已在」且点不动。
- **动作库列表一行的后半句说的是「你」**:「练过 12 次 · 最好 65kg×6」(两个数都从日志算,不存 ——
  存下来就会出现「日志删了这行还在」;一次读日志算两个数)。
  这里有一处**不能图省事的岔路**:那句「最好」**不走纪录榜那张表**(`personalRecords`)——
  它的判据是「够得上纪录榜的维度」(重量 / 1RM / 容量 / 保持),自重动作一条都进不来,
  而列表上最常被翻的恰恰是引体向上、俯卧撑,它们唯一说得出的「最好」是次数。
  所以这一句跟的是**训练页参照行**那条口径(`history.bestOf`,和 `refLine` 的「最好」同一个函数):
  挑动作时看到的数和做的时候看到的数是同一个,不会出现两个「最好」。
  两条附则:没练过的动作**不出现这一句**(不写「最好 —」);助力器械的「重量」按 0 记
  (器械替你分担的力,越大越轻松),它那句只念次数。
- **筛选/搜索的结果一次只铺 80 条,末尾给「加载更多」**(`PAGE_STEP`),铺到 240 条(`PAGE_MAX`)为止,
  再往后换成一句「这么多条翻不到头的,加个器械或部位筛得更快」。两条口径:
  ①全铺会卡 —— 搜「胸」有 262 条、搜「腿」352 条,一屏几千个节点(原来硬截 80 就是为这个),
  改成「先铺 80、想看的人自己往下点」,第一步看到的东西和以前一模一样;
  ②**上限不是为了省节点,是那件事本身**:四百条能一屏翻到底的人,他要的动作在他翻过去之前就出现过了。
  「展开到第几屏」这个状态**自己带着 key**(那一组筛选条件的签名):
  对不上就是新的一组,自然回到第一屏 —— 别改成单独一个 `useState` 再处处记着清(漏一个入口
  就是「切到背还停在第 240 条」),也别用 `useEffect` 清(白闪一帧整个列表);
  签名里**不含收藏与常用次数**:点某行的 ☆ 会把它顶到最前(顺序本来就会变),但不该把展开的两屏收回去。
- **动作库那个搜索框认的不只是动作名**(`engine/search.ts`,三层,前一层 0 结果才轮到后一层):
  ①逐词命中 —— 「哑铃 卧推」要的是**都**有(不是所有哑铃或所有卧推),词序不管;
  ②口语/简写表(`SYNONYMS`)—— 「胸肌」「屁股」「db」「sldl」这些嘴里的词指向库里真有的译名/原文,
  表里每个词都是**拿真数据验过**的(冒烟测试用 `sameSet` 钉「指到的是同一批」,指歪就红);
  ③差一个字的兜底(`nearMatches`)—— 打错一个字(含**相邻两字颠倒**,`sqaut`)只在 0 结果时
  作为「这几个最像」摆三条,不替换结果(猜出来的东西不能长得跟真的一样)。
  英文按**词首**匹配、中文按任意位置:中文没有词边界(搜「背」要能出「下背部」),
  英文按任意位置则满屏假命中(搜 `chin` 出 198 条器**machine**、搜 `row` 出窄距 `narrow`)。
  空格/斜杠/括号/连字符都算间隔,**相邻两段还粘一份** —— 库里同一个动作有写 'pull up' 的
  也有写 'pull-up' 的,两种写法都得搜得到。改这张表/这条判据前先跑 `npm run smoke`。
- **训练日自己也是一个可编辑的东西**(编排页点训练日标题 → 改名 / 上移下移 / 复制 / 删除)。
  「复制」(`engine/editor.ts` 的 `duplicateDay`)有三条口径,改它之前先看注释:
  复制品插在**原件后面**不是排到末尾(排到末尾的话用户点完眼前什么都不变,会以为没生效);
  **key 要重发**(`${key}-2`、`-3`…,照 `plan-text` 导入手写计划的规矩)—— key 才是训练日的身份,
  两天共用一个 key 会「点的是这一天、练的是那一天的处方」;
  **超级组号原样抄过去**(组号只在天内部比较,重发反而把复制品里配好的对拆散),
  但 `holdSec`/`alternates` 这些嵌套字段必须真复制,否则两天共用同一个对象。

### 3. 看变化
```
趋势 tab → 选时间档(7/30/90 天) → 体重 / 训练 / 热量(含三大营养素)/ 步数 → 三条身体下钻
```
这一页上**所有**的块共用同一个时间档。自己另算一个窗口(比如训练块固定按 30 天)
是不允许的 —— 一页上只写着一个「7 天」,里面的图不能各指各的区间。
训练那一块的数据来自分包写的主包快照(`utils/training-progress.ts`),口径同服务端 `GET /trends?range=N`。
饮食那一块下面挂着三大营养素(日均克数 + 供能占比 + 蛋白差多少),口径写在 `utils/nutrition.ts`,
**不要在页面里再算一遍**:日均除以**有记录的天数**(不是窗口天数)—— 同一张卡上
「日均摄入 1800」和「日均蛋白 82g」必须是同几天吃出来的;占比**按热量算不按克数**
(脂肪 9 千卡/克、碳水 4),三项取整后合计必须正好 100(条子是按百分比铺满的,99 会留缝、101 会溢出)。
蛋白的目标由服务端随趋势一起返回(引擎按体重与目标类型算的),**客户端不自己编一个 g/kg 系数**:
同一个数两处算迟早分叉,用户会在两页上看到两个目标。

**全站的折线图只有一种长相**(`components/LineChart`,判据在 `utils/chart.ts`),图上能读出三样东西:
纵轴上下两个刻度 + 横轴首末两个日期、一条**目标线**、以及**手指点哪段报哪个点的读数**(读数写在图下那一行,
没点过时那一行是「点曲线看具体数值」—— 手机上放不下 hover,提示和读数就摆同一个位置)。
三条口径,改之前先读 `utils/chart.ts` 的头注释:
① 刻度、目标线、点选的参考线**全画在 canvas 里**:90 天的曲线要是每个点摆一个 `View`,小程序直接卡死(全站六个调用点共用这一份);
② **目标线画不进来等于没画**,所以算纵轴范围时目标值参与进来(体重一路 70、目标 65,那条线恰恰最该看见);
③ 但目标**太远就不画**(`worthTarget`:它让纵轴跨度涨不过两倍才画)—— 不然「离目标还差 6 公斤」的高度里,
用户一个月掉的 0.5 公斤连一个像素都不到,而他要看的恰恰是那 0.5;「还差多少」由进度环和上面那排数字回答。
点选状态**自带序列签名**(`点数:首标签:末标签`):切 7 天/30 天后「第 5 个点」指的是另一天,签名对不上就当没选过 ——
同列表分页那套「状态自带作用域」。
曲线下面的**日期轴注**只在图里画一份:六个调用点原先各自在图下摆一行首末日期,现在删掉了(围度的 `mc-axis`、单动作曲线的 `eh-axis`)。

## 三、归属规矩(踩过的坑)

1. **一个功能只有一个家。** 同一件事有两个门(记录页一格 + 工具箱一格)时,
   用户不觉得方便,只觉得「怎么又是这个页面」。判断:点进去是不是一个别处到不了的地方。
2. **工具箱只放「工具」,不放数据页和主功能的子页。** 它是「找不到家的东西」的目录,不是全站索引。
   训练的十几个子页曾经全在这儿、和「每日一答」平级;体重数据、围度、进度照片也曾经在这儿 ——
   前者归属错了,后者是**记在记录页、看在趋势页**的东西,两边都已经有门了。
   判断一格该不该留:点进去是不是一个**别处到不了**的地方,且它是个**算的/查的/测的**工具。
3. **同一件事只有一种长相。** 记体重的弹层曾经有两个版本(记录页自己写了一套带历史的,
   其余页面用共用版),于是「删掉记错的那一笔」只有一处能做到。现在只有 `components/WeightSheet` 一份。
4. **数据接口返回的东西要有地方用。** 这类坑踩过两次,症状一模一样:接口给了、库里有,
   页面上却没有一处显示。① 趋势接口一直返回每天的摄入/净热量,页面上没地方看 ——
   这一页就答不了「我这周吃超了没」;② 每笔饮食记录一直带着蛋白/碳水/脂肪
   (食物库有、服务端按天汇总进了 `DailySummary.nutrition`),而**从记录页到趋势页
   没有一处显示过克数** —— 记了两个月只知道「今天 1800 千卡」,答不了「蛋白够不够」。
   两处都补上了:记录的地方看今日合计,看变化的地方看窗口日均与目标。
   **判断方法**:拿接口返回体的字段清单,一个一个在页面上找;找不到的就是这种坑。
5. **跨包的东西住在主包。** 主包不能引用分包;分包写给主包看的快照一律落在 `utils/`
   (`training-digest` / `training-progress` / `workout-draft`),由分包来写、主包只读。
6. **时间是本地的。** 服务端时间戳是 UTC,而用户说的「今天」是本地的 ——
   一律走 `utils/date.todayStr()` / `localDayOf()`,不许 `toISOString().slice(0,10)`。
   东八区早上 8 点前,这两者差一天:早上称的体重记到昨天、凌晨设的目标写成前天、
   导出的文件名带错日期,都是这么来的。窗口口径也只有一个:趋势页选 7 天,
   页面上每一块都按 [今天-6, 今天] 这 7 天算(和服务端 `range` 一致)。
7. **能点的整块要有按下反馈。** 全局样式里列了那些类(见 `styles/global.scss`);
   新加可点容器记得补进去,不可点的**不要**加 —— 按下去有反应却啥也不发生,比没反馈更糟。
8. **别人的东西,署名要跟着东西走。** 动作演示图是 © Gym visual 的第三方素材
   (**有版权、还没拿到许可**,见 `app/scripts/THIRD-PARTY-NOTICES.md` 第 3 节),
   所以「动作图示 © Gym visual · gymvisual.com」那一行是**图的一部分**,和它在同一个组件里
   —— 写在页面页脚不行:训练页速查栏根本没有页脚,于是训练中看的那一次就没有署名了。
   判断方法:把这块东西单独截出来发给别人,该跟着它的那句话还在不在。
9. **能误触出来的东西要能撤。** 训练页里「＋ 加一组」按错一下,那一组会跟着底栏和
   「结束训练」的确认框一直说「还有 1 组没完成」,而用户根本没打算做它 ——
   所以加出来的那一组带一个来路标记(`added`),只有它能撤;计划里本来就有的组不在此列。
   判断标准不是「这个操作能不能删」,而是**这个状态能不能只靠误触产生**:只能靠误触产生的,
   就必须有一条退回去的路,否则用户唯一的选择是走完整场训练去迁就一个手滑。
   **另一类不是误触能产生的,代价在别处:「本次不练这个」。** 它要点开 ⋯ 面板再点一下,
   误触不了 —— 但一旦执行,**已经记下的那些组会跟着没**,而想练回来只能走「加练一个动作」,
   加进来的是计划外的动作(`canProgress` 为假),那些组也就不再参与推导:手抖一下的代价是
   这一整个动作白记。所以它走全站统一的那句确认(「删除记录」「清零重记」问的都是同一套),
   文案跟着「记了几组」改口 —— 没记过组的人只需要知道「计划不受影响」,
   记过组的人得先知道**会丢什么**。判断方法:这个动作**可不可逆**,
   以及不可逆的那部分是不是**用户刚做出来的东西**。
10. **一页上的同一个量只许有一个口径。** 肌群页加「只看有效组」时,那个口径管的是
   **整页**所有出现「组数」的地方(图上的配色、点开的那句详情、练了多少、推拉与上下肢的比例),
   算式全在 `engine/muscles.ts` 里由同一个 `SetMetric` 决定 —— 只换一半是最坏的结果:
   同一页上同一个部位出现两个数,用户会以为其中一个错了。判断方法:新加一个筛选条件后,
   把它管辖的那张卡**从头到尾念一遍**,看还有哪个数字没跟着变。
   两个配套动作:①切换入口摆在它管辖的那几块**上面**(口径变了而界面不说,用户只觉得数在乱跳);
   ②**够不够切**要有话讲 —— 样本太薄时宁可不给这个读法,也不要给一个会被读错的数(`canFilterHard`),
   切不了的时候也得说清楚差在哪,不然那个开关看起来就像坏了。
   **反过来还有一种情况:某个数本来就跟不了这个口径,那就别硬跟。** 肌群页后来加的
   「练得和计划一样吗」,分母是**处方定的组数** —— 处方里没有 RIR 这一档,拿它去比「有效组」
   比出来的是个假差(用户会以为「计划只完成了一半」,其实是另一半留了余量),那正是这一条最坏的形态。
   所以它**不**跟这个开关,而是跟这块卡片**一起收起来**,并在「组数怎么算」那张卡的说明里
   写清楚它去哪了、要跟计划对账就切回来。判断方法:换个口径之后,这个数**还是不是同一个量**;
   不是,就收起来 —— 留着、跟着变、或者干脆换个算法继续摆,三种做法都会让同一页出现两个对不上的数。
11. **写给别处看的快照,要跟着它的输入改口。** 「今天练什么」那张小抄
   (`utils/training-digest.ts`)是分包写给主包看的,原先只在**进计划页时**写一次 ——
   于是「今天不练」点完直接回首页,卡上还是「今天练推日」、日期条上今天那格还是绿的:
   请假这件事只写在 storage 里,没人告诉主包。现在计划页多一个 effect,
   `[plan, logs, dayNotes, assigns]` 一变就重写。注意 hooks 和它打算调的东西都要放在
   `if (!plan) return` **上面**:`useDidShow` 的回调在提前 return 之后照样会跑,
   而 `?off=1` 这条路上它要调的那个函数在那句 return 底下根本没定义 —— 没有计划的人一进来就崩。
   判断方法:凡是「A 写、B 读」的快照,都把 B 显示出来的东西列一遍,再问每一样的输入变了之后
   谁负责重写 —— 答案是「进页面时」的话,那种改完不离开当前页的操作就一定会漏。
12. **同一个说法只要出现一次以上,就得有同一套判据。** 「这次不算进步」先有**整场**那一档
   (发烧、伤后复出:一个开关,但代价是那天所有动作一起作废),后来加了**单个动作**那一档
   (换了台器械、重量不可比;那组只是想活动一下)。两档共用同一个词,就必须共用同一条判据 ——
   所以判据收在 `types.entryCounts`(整场 or 这一条),纪录 / 力量基准 / 力量保持 / 下次目标
   四处都过它。**只挡推导那一处是最像"做完了"的半成品**:日志里那一笔被标着「不算进步」,
   而它照样在你的纪录榜上、照样定着力量基准 —— 那个词在页面上是两个意思。
   两个配套动作:①**露出来的开关要真能做事** —— 计划外的动作(换进来的、加练的)本来就不推导,
   那里不许摆这个开关(`canProgress`),摆了它用户点一下以为自己排除了,其实没这回事;
   ②**"不算"不是"删掉"** —— 组数、容量、热力图、动作曲线照收(那天确实练了),
   这条界线在 `noProg` 的注释里写了两遍,加新统计时照它判。

13. **同一个概念有两套分法时,不要合并,也不要并排 —— 用一个出口把它们串起来。**
    「练哪儿」在全站有两套:动作库的**部位**十档(上臂/前臂分开、大腿/小腿分开,还有颈部与有氧)
    和统计用的**肌群**七组(小臂的动作也归手臂、大腿和小腿分属臀腿与小腿)。
    两套都是对的,只是回答的问题不同 —— 合并(把动作库的筛选改成七个组)会丢掉十档的精度,
    并排(动作库再加一排肌群 chip)则会让用户以为其中一排是多余的,而且两排能叠着筛,
    叠出来的空结果毫无道理可讲。
    做法是给**每套分法各配一个家**,再用一条出口连起来:肌群七组住在肌群页(统计、身体图、
    「练得到背的动作 ›」),部位十档住在动作库;动作库那边**没有肌群 chip 排**,
    肌群筛子只在从肌群页带过来(`?mg=`)时生效,以一条**可关掉的框**出现在结果上方,
    并且**点「部位」里任何一个 chip 都把它清掉**(两句话说的是同一件事,同时生效只会互相矛盾)。
    判断方法:两套分法各说一句「这是什么」—— 说得不一样(「这周练得够不够」vs「这个动作练哪儿」),
    就别合并;说得一样,才是同一套该收一份。
    配套的一条:**筛选的判据要跟统计同源**(`engine/muscles.hitsGroup` 走的是同一个 `groupsOf`,
    所以协同肌也算)—— 统计里给 0.5 组的动作,在这份清单里就该出现,否则「背练得偏少」
    点进去看到的清单和刚看的那个数对不上。

  ①**换口径不动格子图本身** —— 哪天练了是事实(`HeatCell.trained`,一直带着组数),

  图上的配色、那句详情、练了多少、推拉与上下肢),口径在 `engine/muscles.ts` 的 `SetMetric`,

  ②**「练得和计划一样吗」**(实际 vs 计划,差得最多的排最上面)—— 问的是和上面那张不同的另一件事:
  「练了多少」拿的是**大众建议区间**(够不够),这张拿的是**自己的计划**(说好要做的做了没),
  两把尺子摆在一起才看得出差在哪:量在建议区间里、却只有计划的六成,那是计划跟不上自己。

  **套过周期**的计划(`applyCycle(plan).days`)—— 减载周的处方本来就降了一档,传原样的话
  用户刚按计划做完,卡上却说他每个部位都差一截;二是这个数**跟不了「只看有效组」**,
  所以整块跟着收起来(理由见上面第 10 条)。
  ③「缓过来没有」按疲劳算,不数组数 —— 和①②是三种量。
  ④这一页**有出口**:点开某个部位时,详情框里那条「练得到背的动作 ›」带 `?mg=back` 进动作库。
  没有它,这一页只能说出一句结论(「背练得偏少」),补救的动作(翻动作库、找背的动作)
  全得用户自己走过去 —— 判断依据还是那条:「点进去的下一步,用户想不想得到」。
